# Contributing to rust-jexl3

The one rule: **the jar decides.** rust-jexl3 aims to behave exactly like
`commons-jexl3-3.2.1.jar`. A change is right when it makes the port agree with the jar on a case
the jar can run, and wrong when it makes them disagree -- whatever the Java source seems to say.

## Reporting a difference from Java JEXL

The most useful thing anyone can send. Please include:

1. **The expression or script**, exactly as you ran it.
2. **The variables** it saw (names, values and their Java types -- `Integer` and `Long` behave
   differently in JEXL), and the engine options (`strict`, `silent`, `safe`, namespaces ...).
3. **What Java JEXL 3.2.1 returns**, and what rust-jexl3 returns: the value with its type, or the
   exception class and its exact message.

If you can run the oracle, a case in its JSON format settles it at once:

```sh
oracle/build.sh                      # once; needs a JDK and Maven (fetches the 3.2.1 jar)
echo '{"id":"x","kind":"script","src":"1 + 1","ops":["exec"],"ctx":{"a":{"t":"Integer","v":"2"}}}' \
  | oracle/target/oracle
```

and the same case through the port:

```sh
echo '<the case>' > /tmp/c.jsonl && oracle/target/oracle < /tmp/c.jsonl > /tmp/e.jsonl
EXEC_CASES=/tmp/c.jsonl EXEC_EXPECTED=/tmp/e.jsonl cargo test --release --test exec_oracle execution_matches
```

Please do not attach production data you are not free to publish; a reduced, synthetic case is
better anyway.

## Before a pull request

```sh
sh tools/verify.sh          # build, clippy -D warnings, package, every suite, privacy check
sh tools/verify.sh --full   # adds the upstream corpus and a fresh 8,000-case sample (needs the JVM oracle)
```

- **Test first.** A fix starts as a case the jar answers and the port gets wrong: add it to a
  fixture (or `tests/upstream_*.rs`), watch it fail, then fix.
- **Measure, don't guess.** When a message or a value differs, read the Java that produces it and
  check the claim on the JVM. Several fixes here came from a null turned into `""` or `"?"` deep in
  a constructor.
- **The baseline.** `tests/data/exec/known_mismatches.txt` lists understood differences; the replay
  fails on any difference not listed *and* on a listed one that starts to match. A fix removes its
  line. `not_comparable.txt` is only for cases whose Java answer changes from one JVM run to the
  next -- say why in the line.
- **Where to put things.** One Rust module per Java class, first line
  `// port of: org.apache.commons.jexl3.<package>.<Class>`, methods in the Java order.
- Generated files (`src/parser/*_gen.rs`, `src/java/character_data.rs`, fixtures under
  `tests/data/`) are regenerated by their tools, not edited by hand; PROGRESS.md lists the commands.
